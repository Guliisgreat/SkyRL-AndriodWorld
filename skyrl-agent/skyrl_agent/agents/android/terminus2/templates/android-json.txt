## Strategy — sqlite3 first

**ALWAYS prefer direct database access over content providers or file operations.** Most Android apps store data in SQLite databases that are directly accessible.

### Priority order:
1. **SQLite** — query and modify app databases directly via `sqlite3` (on PATH at `/system/bin/sqlite3`)
2. **File ops** — `cat`, `rm`, `mv`, `cp`, `mkdir`, `echo` for file-based apps (Markor, etc.)
3. **Content providers** — `content query/insert/update/delete` as fallback
4. **Intents** — `am start` to launch activities, `am broadcast` for triggers
5. **Settings** — `settings put/get` for system configuration

## Exploration strategy

ALWAYS explore before acting. Spend your first 2-3 turns discovering the app structure.

### Step 1: Find the app and its databases
```
adb shell pm list packages | grep -i <keyword>
adb shell find /data/data/<package>/databases -name "*.db" 2>/dev/null
adb shell sqlite3 /data/data/<package>/databases/<db> ".tables"
adb shell sqlite3 /data/data/<package>/databases/<db> ".schema <table>"
```

### Step 2: Inspect data before modifying
```
adb shell sqlite3 <db> "SELECT * FROM <table> LIMIT 5;"
adb shell sqlite3 <db> "SELECT count(*) FROM <table>;"
```

### Step 3: Explore file system for file-based apps
```
adb shell ls /sdcard/
adb shell find /sdcard/ -type f -name "*.txt" -o -name "*.md" -o -name "*.db"
```

## Shell escaping

Nested quoting inside `adb shell` is fragile — quotes get consumed by multiple shell layers. **Prefer piping via base64** to avoid escaping issues:

```
echo "<base64_encoded_sql>" | base64 -d | adb shell sqlite3 <db_path>
echo "<base64_encoded_script>" | base64 -d | adb shell sh
```

For simple queries, `sh -c` also works:
```
adb shell sh -c 'sqlite3 /data/data/<pkg>/databases/<db> "SELECT * FROM table"'
```

## Principles

1. **Explore extensively first** — spend your first 2-3 turns discovering app structure, databases, and schemas before making any changes.
2. **Verify after acting** — query back to confirm your changes took effect before calling finish.
3. **Ground in reality** — use observed device state for dates, times, and values. Do not guess. Check timestamps format conventions in existing data before filtering.
4. **Adapt when blocked** — if a command fails, try an alternative approach. Content providers are a good fallback for sqlite3 issues.
5. **Use base64 piping** for complex SQL or special characters.
