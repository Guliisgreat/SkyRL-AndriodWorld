## CRITICAL: Shell Escaping

Nested quoting inside `adb shell` breaks — quotes get consumed by multiple shell layers.

### For schema exploration — echo-pipe is fine:
```
adb shell "echo '.tables' | sqlite3 /data/data/<package>/databases/<db>"
adb shell "echo '.schema <table>' | sqlite3 /data/data/<package>/databases/<db>"
adb shell "echo 'SELECT * FROM <table> LIMIT 5;' | sqlite3 /data/data/<package>/databases/<db>"
```

### For complex SQL with parentheses, quotes, or special characters — use base64:
When SQL contains `(`, `)`, `'`, or `"`, **base64-encode it** to bypass all shell escaping:
```
echo "<base64_encoded_sql>" | base64 -d | adb shell sqlite3 /data/data/<package>/databases/<db>
```
Example — to run `INSERT INTO recipes (title,servings) VALUES ('Pasta',4);`:
1. Base64-encode the SQL: `echo -n "INSERT INTO recipes (title,servings) VALUES ('Pasta',4);" | base64` → `SU5TRVJUIElOVE8g...`
2. Run: `echo "SU5TRVJUIElOVE8g..." | base64 -d | adb shell sqlite3 /data/data/<pkg>/databases/<db>`

This works for ANY SQL — INSERT, DELETE with WHERE IN(...), UPDATE with quotes, etc. Use it whenever echo-pipe gives syntax errors.

### Writing file content with special characters — use base64:
```
echo "<base64_of_content>" | base64 -d | adb shell "cat > /path/to/file"
```

### Multi-step file operations — use simple sequential commands:
```
adb shell cat /path/file1 > /tmp/merged
adb shell cat /path/file2 >> /tmp/merged
adb shell cp /tmp/merged /path/output
```
Do NOT use complex one-liners with awk/sed or heredoc syntax (`cat <<EOF`) — they break.

**NEVER** use: `adb shell sqlite3 <db> "SQL"` (nested quotes break) or heredoc (`cat <<EOF`).

**NEVER** use this broken pattern (it will always fail with syntax errors):
```
adb shell sqlite3 <db> "SELECT * FROM table;"   # WRONG — nested quotes break
```

## Strategy — sqlite3 first

**ALWAYS prefer direct database access over content providers or file operations.** Most Android apps store data in SQLite databases that are directly accessible.

### Priority order:
1. **SQLite** — query and modify app databases directly via `sqlite3`. Always use echo-pipe pattern.
2. **File ops** — `cat`, `rm`, `mv`, `cp`, `mkdir`, `printf` for file-based apps
3. **Content providers** — `content query/insert/update/delete` as fallback
4. **Intents** — `am start` to launch activities, `am broadcast` for triggers
5. **Settings** — `settings put/get` for system configuration

### Common system database paths:
```
/data/data/com.android.providers.calendar/databases/calendar.db
/data/data/com.android.providers.contacts/databases/contacts2.db
/data/data/com.android.providers.telephony/databases/mmssms.db
/data/data/com.android.providers.settings/databases/settings.db
```

## Exploration strategy

ALWAYS explore before acting. Spend your first 2-3 turns discovering the app structure — then **act immediately**. Do not spend more than 3 turns exploring.

### Step 1: Find the app and its databases
```
adb shell pm list packages | grep -i <keyword>
adb shell find /data/data/<package>/databases -name "*.db" 2>/dev/null
adb shell "echo '.tables' | sqlite3 /data/data/<package>/databases/<db>"
adb shell "echo '.schema <table>' | sqlite3 /data/data/<package>/databases/<db>"
```

If `/data/data/<package>` is not accessible (non-debuggable), try:
```
adb shell find /sdcard/Android/data/<package> -name "*.db" 2>/dev/null
adb shell ls /data/user/0/<package>/databases/ 2>/dev/null
```

### Step 2: Inspect data, then act
```
adb shell "echo 'SELECT * FROM <table> LIMIT 5;' | sqlite3 /data/data/<package>/databases/<db>"
```
Once you understand the schema and data, **immediately execute** the required INSERT/UPDATE/DELETE. Do not over-explore.

### Step 3: Explore file system for file-based apps
```
adb shell ls /sdcard/
adb shell find /sdcard/ -type f -name "*.txt" -o -name "*.md"
```

## Date & Time

Before any temporal reasoning, run `date` on the device to get the current date, time, and timezone. Then:
- Convert "today", "this week", "next week", etc. to concrete date ranges using the device clock, not your own knowledge.
- Use the device's timezone for all timestamp conversions. Unix timestamps in databases are often UTC — convert both sides to the same zone before comparing.
- **Check timestamp units**: Examine existing data first. If values are ~13 digits (e.g., 1697500000000), they are milliseconds. If ~10 digits (e.g., 1697500000), they are seconds. Some apps use one, some the other — always verify before computing ranges.
- For range queries use `>= start AND < end` (half-open interval), not `BETWEEN`.
- "Next" means the first occurrence strictly after the current device time.

## Database Write Operations

When you need to INSERT, UPDATE, or DELETE rows:
1. First discover the schema with `.schema <table>`.
2. Examine existing rows to understand the data format (column types, ID patterns, required fields).
3. **Execute the write immediately** — use echo-pipe for simple writes, base64 for complex ones with special characters.
4. After the write, **query back** to verify the change persisted.
5. **Force-stop** the app so it re-reads from disk: `am force-stop <package>`.

For calendar events, INSERT directly into the events table — use the same column values and timestamp format you observed in existing rows.

For expense/financial apps, amounts may be stored as **integers in cents** (e.g., $57.47 → 5747). Check existing data to confirm the format.

## File Operations

When creating or modifying files that an app should detect:
- Use `printf '%s' 'content'` or base64 to write content — safer than `echo` with special characters.
- After writing files, trigger a media scan: `am broadcast -a android.intent.action.MEDIA_SCANNER_SCAN_FILE -d file://<path>`
- After creating or deleting files in an app's directory, force-stop the app: `am force-stop <package>`.
- When merging files, use simple sequential `cat file1 > out` then `cat file2 >> out`. Verify by reading the output.
- For cross-app tasks, break into discrete steps: (1) extract data, (2) discover target schema, (3) write data, (4) verify.

## Messaging & Communication

When sending messages (SMS, etc.) without UI interaction:
- Use the `service call` interface instead of direct DB writes. For SMS: `service call isms 7 i32 0 s16 "com.android.mms" s16 "<phone>" s16 "null" s16 "<body>" s16 "null" s16 "null"` — this actually dispatches the message through the telephony stack.
- Always check the SMS content provider afterward: `content query --uri content://sms --where "address='<phone>'"` to verify the message was recorded.
- For contacts, use the contacts content provider: `content insert --uri content://com.android.contacts/raw_contacts` followed by data inserts for name, phone, etc.

## App State Sync

After modifying any app's data (database writes, file operations, content provider inserts):
- Force-stop the app: `am force-stop <package>`.
- If verification requires the app to have processed the data, restart it: `am start -n <package>/<activity>` (discover the main activity via `dumpsys package <package> | grep -A5 'android.intent.action.MAIN'`).
- Wait briefly, then verify through the app's content provider or database that the state is as expected.
